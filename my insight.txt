NexusLake Agentic Architect — Antigravity Master Skill
NexusLake Agentic Architect
1. Mission

Build NexusLake Agentic Architect as an AI-native data estate modernization platform.

The platform transforms heterogeneous enterprise data estates into an open, governed and AI-ready Apache Iceberg lakehouse on Google Cloud.

The system must support an extensible range of:

Relational databases
Cloud databases and warehouses
NoSQL databases
Files and object storage
Semi-structured data
Streaming and CDC sources
Unstructured and multimodal data

Do not design the system around one database vendor.

The core abstraction is the DataAsset, not a specific database technology.

2. Core Product Lifecycle

The platform follows this 12-stage lifecycle:

Discover → Assess → Understand → Decide → Design → Clean → Transform → Migrate → Validate → Govern → Operate → Visualize

Every major feature should map to one or more lifecycle stages.

The system must also support a continuous operational loop:

Observe → Analyze → Optimize → Revalidate

This is not a separate lifecycle stage. It continuously operates after migration.

3. Core Architecture

Use four major architectural planes.

3.1 Agentic Control Plane

Responsible for:

Gemini-powered reasoning
Agent orchestration
Planning
Decision making
Policy evaluation
Human approval
Migration planning
Natural-language interaction
Auditability

Preferred Google technologies:

Gemini
Google ADK where appropriate
Google Antigravity during development
Cloud Run and/or GKE for deployed services
IAM
Secret Manager
Cloud Logging
Cloud Monitoring

Never allow an LLM to directly execute unrestricted production operations.

3.2 Data Intelligence Plane

Responsible for understanding the estate.

Maintain a canonical representation containing:

DataAsset
 ├── Identity
 ├── SourceSystem
 ├── Schema
 ├── Statistics
 ├── Relationships
 ├── Lineage
 ├── BusinessMeaning
 ├── SecurityClassification
 ├── DataQuality
 ├── Freshness
 ├── WorkloadProfile
 ├── Dependencies
 ├── MigrationConstraints
 └── RecommendedStrategy

Use deterministic metadata wherever possible.

Gemini should reason over this structured representation rather than repeatedly scanning raw systems.

3.3 Execution Plane

Gemini decides and plans.

Deterministic Google Cloud services execute.

Potential technologies include:

Serverless Spark
Dataflow
Datastream
Cloud Storage
BigQuery
Apache Iceberg
BigLake Iceberg REST Catalog
Pub/Sub

Do not implement data movement inside the LLM layer.

3.4 Lakehouse Plane

Use an open architecture based on:

Cloud Storage
      ↓
Apache Iceberg
      ↓
BigLake Iceberg REST Catalog
      ↓
BigQuery / Spark / Trino / Flink

Avoid unnecessary proprietary coupling.

The design should preserve interoperability with standard Iceberg engines.

4. Universal Connector Architecture

Never hard-code migration logic directly into individual agents.

Create a connector/adapter abstraction.

Each connector should expose capabilities such as:

discover()
validate_connection()
extract_schema()
extract_statistics()
extract_lineage()
profile()
estimate_volume()
estimate_cost()
read_data()
capture_changes()

Create a common interface such as:

class SourceConnector:
    ...

The architecture must allow new connectors to be added without changing the core orchestration system.

Initial demonstration connectors should be limited to a practical MVP, for example:

PostgreSQL
MongoDB
Parquet
JSON

Additional connectors can be added later.

Do not claim that every enterprise database is already supported unless an implementation exists.

5. Canonical Data Estate Model

Create a technology-neutral internal model.

    dependencies: list
    constraints: list

The model must be extensible.

Do not make the internal model dependent on PostgreSQL, MongoDB, Oracle, etc.
